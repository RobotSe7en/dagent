# Core Concepts

dagent separates declarative configuration from runtime ownership. This keeps
agent objects lightweight while making execution state, capabilities, review,
and continuation explicit.

## Runner

`Runner` is the public SDK entrypoint for execution. It owns:

- the provider
- the capability catalog
- MCP server registration
- skill discovery and managed installs
- profile roots
- runtime state and traces
- review continuations

Construct `Runner(...)` directly when your application supplies configuration in
code. Use `Runner.from_config(...)` when provider settings, MCP servers,
validation, or profile directories should come from a YAML file.

## Declarative Agents

`ToolAgent`, `AutoAgent`, and `DagAgent` are immutable run targets. They declare
which profile, capabilities, skills, bounds, and review level a run should use.
They do not own provider clients, sessions, or capability handlers.

## Tool Loops and Dynamic DAGs

`ToolAgent` performs bounded tool-loop work. It is a good fit when each next
action depends on the latest observation.

`DagAgent` asks the model for a strict typed plan, normalizes it to `DAGSpec`,
executes ready layers, observes results, and replans locally when needed.
The default `typed_spec` frontend keeps model output to capability and condition
nodes, branch or conditional-gate edges, artifacts, and value expressions. The optional
`sdk_builder` frontend can additionally author maps, subgraphs, and bounded
loops. Both normalize to the same static-DAG execution contracts.

`AutoAgent` lets the runtime choose direct tool use or dynamic DAG planning for
each request.

## Static DAGs

`Dag` is for workflows whose graph shape belongs in code. Static DAGs use typed
graph input, explicit `dag.add_edge(...)` dependencies, structured `$expr` value
references, artifact declarations, boundaries, exclusive condition nodes,
conditional edge gates, map fan-out,
subgraphs, and bounded loops.

## Capabilities

Capabilities are executable things known to the runner:

- Python tools use `tool.<name>` ids.
- MCP tools use `mcp.<server>.<tool>` ids.
- Built-in skill accessors use `skill.list` and `skill.view`.

Agents receive an allowlist of capability ids or `@dagent.tool` bindings. The
runtime executes all capability kinds through the shared capability executor.

## Skills

Skills are readable instructional assets discovered from skill roots or managed
installs. They are not executable capabilities by themselves. Agents use
`skills=[...]` to limit which concrete skills are visible through `skill.list`
and `skill.view`.

## Results, State, and Review

`Runner.run(...)` returns `RunResult` for every public target. Agent runs accept
OpenAI-compatible `messages`; static DAG runs accept `graph_input`.

`RunResult.messages` contains messages generated by the current run. Caller code
owns the conversation list and should append generated messages when continuing
an agent conversation. `RunResult.state` contains dagent's resumable internal
state, including trace data and pending review checkpoints.

When work requires review, approve or reject with `Runner.resume(...)` or
`Runner.resume_stream(...)`. For cross-process continuation, persist
`RunResult.checkpoint`; it keeps mutable state, resolved target semantics, and
cumulative `ExecutionUsage` telemetry separate. Execution bounds belong to the
agent declaration through its single `max_steps` field; static DAGs have no
root-wide operation limit, while Map and Loop nodes retain their structural
bounds. See
[Results, Streaming, and Review](results-streaming-review.md).
